# 画面定位引擎优化改造方案

## 1. 背景

当前项目的画面定位模块位于 `4_visual_alignment_engine/run.py`，核心目标是把参考解说视频中的 `ref_shots` 定位到原电影的 `movie_shots`，输出 `ref_to_movie_timeline.json`。后续 `5_script_visual_binder`、`7_timeline_composer` 和视频生成链路都会依赖这个定位结果。

当前实现采用：

```plain
参考镜头关键帧
  -> 与原电影镜头关键帧逐个比较
  -> 计算视觉相似度
  -> 叠加时间连续性
  -> 输出最佳 movie_shot
```

视觉特征来自 `utils/visual_features.py`：

| 特征 | 当前作用 | 权重 |
| --- | --- | --- |
| dHash | 快速判断整体结构是否相似 | 0.45 |
| HSV 直方图 | 判断整体颜色分布是否相似 | 0.35 |
| ORB | 判断局部特征点是否匹配 | 0.20 |

综合分：

```plain
visual_score = hash_score * 0.45 + hist_score * 0.35 + orb_score * 0.20
final_score = visual_score * 0.7 + continuity_score * 0.3
```

命中条件目前只看 `visual_score >= min_score`，默认阈值为 `0.35`。

## 2. 当前问题

### 2.1 只使用第一个关键帧

当前 `first_keyframe()` 只取每个镜头的第一个关键帧。这个策略简单，但在影视解说场景里容易失真：

- 第一帧可能是转场黑帧、闪白、字幕遮挡或运动模糊。
- 解说视频常见裁切、缩放、调色、压缩，单帧匹配容易不稳定。
- 一个镜头内部可能有明显运动，开头和中段画面差异很大。

结果是：一个不具代表性的关键帧会直接决定整个镜头的定位结果。

### 2.2 贪心匹配容易连锁错误

当前每个参考镜头独立选最优候选，只通过 `prev_match` 加一点时间连续性修正。如果某个镜头错配，后续镜头会被错误的 `prev_match` 牵引，出现连续错位。

这类错误在长片段中比较危险，因为后续模块会把错误位置继续传给 `script_mapping`、`final_timeline`，最终影响生成视频剪辑。

### 2.3 全量两两比较效率有限

当前复杂度接近：

```plain
len(ref_shots) * len(movie_shots)
```

如果原电影镜头较多，每个参考镜头都要和全部原片镜头比较。短视频还能接受，电影级素材会越来越慢。

### 2.4 视觉特征鲁棒性不足

dHash 和颜色直方图对以下变化比较敏感：

- 上下黑边或左右裁切。
- 滤镜调色、亮度变化。
- 解说视频二次压缩。
- 贴纸、水印、字幕条。
- 画面缩放和局部重构图。

ORB 能补一点局部结构，但在低纹理、运动模糊、暗光画面里也不稳定。

### 2.5 分数解释不够完整

当前候选输出已有 `hash`、`hist`、`orb` 细节，这是好的基础。但缺少这些排查字段：

- 当前候选的视觉排名。
- 当前候选的综合排名。
- 与上一个命中点的时间偏差。
- 第一名和第二名的差距。
- 是否因为连续性被提升。
- 是否因为视觉分不足被拒绝。

定位一旦失败，人工判断和自动调参都不够方便。

## 3. 改造目标

这次优化不只是提高单点相似度，而是让定位结果更稳定、更可解释、更适合后续自动生成。

目标分为四层：

| 层级 | 目标 | 说明 |
| --- | --- | --- |
| 召回层 | 不漏掉真实候选 | 用多关键帧和轻量特征扩大可靠候选 |
| 精排层 | 选出更像的镜头 | 引入多特征融合和必要的深度视觉特征 |
| 路径层 | 避免局部错配 | 用全局路径优化替代单步贪心 |
| 诊断层 | 方便审核和回归 | 输出可解释字段、低置信度原因和候选截图 |

## 4. 推荐总体方案

### 4.1 多关键帧特征

把每个 shot 的特征从单帧扩展为多帧：

```json
{
  "shot_id": "movie_shot_000041",
  "start": 125.3,
  "end": 128.1,
  "keyframes": [
    "start.jpg",
    "middle.jpg",
    "end.jpg"
  ],
  "features": [
    {"frame_role": "start", "feature": {}},
    {"frame_role": "middle", "feature": {}},
    {"frame_role": "end", "feature": {}}
  ]
}
```

镜头之间的视觉分不再是单帧对单帧，而是多帧聚合：

```plain
frame_pair_scores = compare(each ref frame, each movie frame)
shot_score = max(frame_pair_scores) * 0.6 + avg(top3(frame_pair_scores)) * 0.4
```

这样可以保留“某一帧非常像”的能力，又避免偶然高分完全主导。

### 4.2 两阶段候选召回与精排

第一阶段用轻量特征快速召回：

```plain
dHash + HSV hist -> top_k movie shots
```

第二阶段只对候选做更重的匹配：

```plain
ORB / SIFT / CLIP embedding -> rerank
```

推荐默认参数：

| 参数 | 建议值 | 说明 |
| --- | --- | --- |
| `recall_top_k` | 80 | 每个参考镜头召回原片候选数 |
| `rerank_top_k` | 20 | 精排后保留候选数 |
| `output_top_n` | 8 | 输出给 JSON 的候选数 |

### 4.3 增加深度视觉特征

建议在 OpenCV 传统特征之外，增加可选的 embedding 特征。

优先级：

| 方案 | 优点 | 风险 |
| --- | --- | --- |
| CLIP image embedding | 对裁切、调色、语义相似更稳 | 需要模型依赖，速度和体积增加 |
| DINOv2 embedding | 更偏视觉结构，适合画面匹配 | 模型依赖更重 |
| OpenCV SIFT | 局部特征比 ORB 更稳 | 仍受低纹理和遮挡影响 |

建议先做成可选能力：

```plain
--feature-mode classic
--feature-mode classic_clip
```

默认保留 `classic`，避免破坏当前轻量运行方式。

### 4.4 全局路径优化

当前是逐镜头贪心：

```plain
for ref_shot:
    choose best movie_shot
```

建议改成候选图上的动态规划：

```plain
每个 ref_shot 保留 top_k 候选
候选节点分数 = visual_score
候选转移分数 = time_continuity + monotonic_penalty + jump_penalty
求整体最高分路径
```

路径分数：

```plain
path_score(i, j) =
  visual_score(i, j) * visual_weight
  + transition_score(prev_j, j) * transition_weight
  - penalties
```

关键约束：

| 约束 | 说明 |
| --- | --- |
| 时间单调 | 默认不允许当前候选大幅早于上一个原片位置 |
| 间隔相似 | 参考镜头间隔和原片候选间隔越接近越好 |
| 跳跃惩罚 | 大幅跳到远处需要更高视觉分支撑 |
| 重复惩罚 | 多个参考镜头重复命中同一 movie_shot 时降分 |

这样能避免一个局部高分镜头破坏整体时间线。

### 4.5 动态阈值和置信度

当前只用固定 `min_score`。建议结合分数分布：

```plain
best_visual_score
second_visual_score
score_gap = best - second
path_consistency
```

置信度规则建议：

| confidence | 条件 |
| --- | --- |
| high | `visual_score >= 0.82` 且 `score_gap >= 0.08` 且路径连续 |
| medium | `visual_score >= 0.65` 或路径连续性强 |
| low | 分数低、候选接近、路径跳跃或需要兜底 |

`status` 建议拆得更细：

```plain
matched
matched_low_confidence
inferred_by_neighbors
unmatched
needs_review
```

## 5. 输出结构优化

推荐保留当前 `ref_to_movie_timeline` 顶层结构，新增诊断字段，减少对下游的破坏。

示例：

```json
{
  "ref_to_movie_timeline": [
    {
      "ref_shot_id": "ref_shot_001",
      "ref_start": 0.0,
      "ref_end": 2.8,
      "movie_start": 125.3,
      "movie_end": 128.1,
      "movie_shot_ids": ["movie_shot_000041"],
      "match_score": 0.92,
      "final_score": 0.89,
      "match_type": "global_path",
      "confidence": "high",
      "status": "matched",
      "diagnostics": {
        "visual_rank": 1,
        "final_rank": 1,
        "score_gap": 0.14,
        "time_delta": 0.3,
        "path_penalty": 0.0,
        "accepted_reason": "visual_score_high_and_path_continuous"
      },
      "candidates": []
    }
  ],
  "metadata": {
    "algorithm_version": "visual_alignment_v2",
    "feature_mode": "classic",
    "recall_top_k": 80,
    "rerank_top_k": 20
  }
}
```

注意：`movie_start`、`movie_end`、`movie_shot_ids`、`status`、`confidence` 应继续保留，保证 `5_script_visual_binder` 和后续时间轴模块可以平滑读取。

## 6. 和视频生成服务的关系

`utils/generate_video/video_generation_service.py` 的生成逻辑最终会根据项目脚本里的 `segments` 进行剪辑、配音和拼接。也就是说，画面定位模块虽然不直接剪视频，但它会通过以下链路影响最终生成：

```plain
ref_to_movie_timeline
  -> script_mapping
  -> final_timeline / project.script.segments
  -> VideoGenerationService.generate_from_script()
  -> ffmpeg 剪辑与拼接
```

因此定位优化要特别关注三个下游稳定性问题：

| 风险 | 对生成视频的影响 | 处理建议 |
| --- | --- | --- |
| 定位错位 | 剪出来的画面和文案不匹配 | 低置信度进入审核或邻近补齐 |
| 时间段过短 | 配音替换时画面不够用 | `7_timeline_composer` 扩展相邻镜头 |
| 多段重复命中 | 成片画面重复、节奏异常 | 路径优化加入重复惩罚 |

生成服务不应该直接承担画面定位纠错。更合理的边界是：

- 画面定位模块负责产出可信的原片时间范围。
- 时间轴模块负责根据 TTS 时长扩展或裁剪画面。
- 视频生成服务只消费最终脚本，负责稳定剪辑、配音、拼接和错误上报。

## 7. 分阶段落地计划

### 阶段一：低风险增强

目标：不引入大模型，不改变下游接口。

改造项：

- `first_keyframe()` 改为 `select_keyframes()`，支持取多个关键帧。
- 新增 `build_shot_feature()`，缓存一个镜头的多帧特征。
- 新增 `compare_shot_features()`，用多帧聚合得到 shot-level 分数。
- 输出 `score_gap`、`time_delta`、`accepted_reason`。
- 保持 `ref_to_movie_timeline.json` 兼容当前字段。

验收标准：

- 原有命令仍能跑通。
- 输出 JSON 字段向后兼容。
- 同一批测试素材下，`unmatched` 数量不增加。
- 明显转场帧导致的错配减少。

### 阶段二：候选召回和路径优化

目标：提升长视频稳定性，减少连锁错配。

改造项：

- 每个参考镜头先召回 `recall_top_k` 个候选。
- 对候选做精排并保留 `rerank_top_k`。
- 基于 top-k 候选做动态规划路径搜索。
- 加入时间单调、跳跃、重复命中惩罚。
- `match_type` 新增 `global_path`、`neighbor_inferred`。

验收标准：

- 长片段中不出现大面积时间线倒退。
- 单个错配不再明显拖坏后续镜头。
- 候选输出可解释，人工能看出为什么选择该镜头。

### 阶段三：可选深度特征

目标：处理裁切、调色、字幕遮挡明显的素材。

改造项：

- 新增 embedding 特征接口。
- 支持 `--feature-mode classic_clip`。
- embedding 缓存到输出目录，避免重复计算。
- 配置模型路径和设备参数。

验收标准：

- 无模型时仍可使用 `classic` 模式。
- 有模型时困难素材定位准确率提升。
- 缓存命中后重复运行速度明显提升。

### 阶段四：审核和回归工具

目标：让定位问题能被快速发现、复现和修正。

改造项：

- 生成候选对比图：参考帧 + top candidates。
- 输出低置信度报告。
- 增加一组固定测试素材的回归结果。
- 支持人工覆写映射表。

人工覆写格式建议：

```json
{
  "overrides": [
    {
      "ref_shot_id": "ref_shot_012",
      "movie_shot_id": "movie_shot_000153",
      "reason": "manual_review"
    }
  ]
}
```

## 8. 模块设计建议

建议把当前逻辑拆成更清晰的内部模块：

```plain
utils/visual_features.py
  - 单帧特征
  - 多帧特征
  - 特征比较

4_visual_alignment_engine/candidate_recall.py
  - 轻量召回

4_visual_alignment_engine/rerank.py
  - 候选精排

4_visual_alignment_engine/path_solver.py
  - 动态规划路径优化

4_visual_alignment_engine/diagnostics.py
  - 诊断字段和审核报告

4_visual_alignment_engine/run.py
  - CLI 参数
  - 读取输入
  - 组织流程
  - 写出结果
```

这样 `run.py` 不会继续变重，后续也方便单测。

## 9. CLI 参数建议

保留现有参数：

```plain
--top-n
--min-score
```

新增参数：

```plain
--keyframes-per-shot 4
--recall-top-k 80
--rerank-top-k 20
--feature-mode classic
--disable-global-path
--manual-overrides overrides.json
--diagnostics-dir outputs/4_visual_alignment_engine/diagnostics
```

默认行为建议：

- 默认启用多关键帧。
- 默认启用全局路径优化。
- 默认不启用深度模型。
- 默认输出诊断字段，但不生成大量图片，避免输出目录膨胀。

## 10. 测试计划

### 单元测试

| 测试对象 | 测试内容 |
| --- | --- |
| `compare_features` | 分数范围稳定在 0 到 1 |
| `compare_shot_features` | 多帧聚合不被单个坏帧完全拖垮 |
| `path_solver` | 时间单调路径优先于局部孤立高分 |
| override 逻辑 | 人工指定结果优先级最高 |

### 集成测试

准备三类素材：

| 类型 | 目的 |
| --- | --- |
| 参考视频和原片几乎一致 | 验证基础定位 |
| 有字幕、裁切、调色 | 验证鲁棒性 |
| 有跳剪和重复画面 | 验证路径优化 |

关键指标：

```plain
matched_rate
high_confidence_rate
manual_review_rate
average_score_gap
timeline_backward_count
duplicate_movie_shot_count
```

### 下游回归

至少跑通：

```plain
1_reference_analyzer
3_movie_shot_parser
4_visual_alignment_engine
5_script_visual_binder
7_timeline_composer
generate_from_script
```

检查点：

- `script_mapping` 能读取新字段并忽略不认识的诊断字段。
- `final_timeline` 中的 `movie_start`、`movie_end` 合法。
- 视频生成阶段不会因为低置信度字段变化而失败。

## 11. 风险和取舍

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| 运行时间增加 | 多关键帧和精排会更慢 | 缓存特征、两阶段召回 |
| 模型依赖变重 | CLIP/DINOv2 增加安装成本 | 做成可选模式 |
| 路径优化过度纠偏 | 强行保持连续可能错过真实跳剪 | 给高视觉分候选跳跃豁免 |
| 输出结构变复杂 | 下游读取可能受影响 | 只新增字段，不删除旧字段 |
| 人工审核成本 | 低置信度变多时需要审核 | 输出对比图和明确原因 |

## 12. 推荐实施顺序

建议先做：

```plain
多关键帧匹配
  -> 诊断字段增强
  -> top-k 候选召回
  -> 全局路径优化
  -> 可选深度特征
```

不建议第一步就上深度模型。当前系统最明显的短板是单关键帧和贪心路径，先解决这两个，收益更直接，也不会显著增加部署复杂度。

## 13. 最小可交付版本

第一版可以只交付以下内容：

- `select_keyframes(item, max_frames=3)`
- `build_shot_feature(item)`
- `compare_shot_features(ref_feature, movie_feature)`
- `diagnostics.score_gap`
- `diagnostics.time_delta`
- 保持现有 JSON 兼容

这版完成后，画面定位会从“单帧猜测”升级为“镜头级匹配”，是投入产出比最高的一步。
